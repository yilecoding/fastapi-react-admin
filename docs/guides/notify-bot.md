# 群机器人：接一个飞书机器人，再练一道设计题

这份文档分两半：

1. **动手**：把一个飞书群的自定义机器人接进来，发出第一条消息（约 10 分钟）
2. **动脑**：这个功能是怎么一步步设计出来的，然后留两道设计题，照同样的路子自己走一遍

功能本身在 v0.9.0（#184，#166 二期）。实现细节和踩过的坑在
[`plugin/notification` 分册](../../apps/api/backend/plugin/notification/AGENTS.md)「群机器人」一节。

---

## 第一部分：接一个飞书机器人

### 0. 先准备好服务端

群机器人的 Webhook 地址要加密保存，加密密钥在 `apps/api/backend/.env`：

```bash
python -c "import os;print(os.urandom(32).hex())"
# 把输出写进 .env：
NOTIFICATION_ENCRYPT_SECRET_KEY='刚才那一串'
```

改完重启后端。没配的话，新增机器人的表单顶上会直接提示「存不进去」。

另外确认 **Celery worker 在跑**（`pnpm dev` 会一起起 api、web、worker 三个进程）。
「发测试消息」是接口里直接发的，不需要 worker；但真实的通知（公告、审批结果）是 worker 从投递表里取出来发的 ——
worker 没起，投递记录会一直停在「待发」。

### 1. 在飞书群里建机器人

桌面端飞书：

1. 打开要接收通知的群 → 右上角「⋯」→ **设置** → **群机器人** → **添加机器人**
2. 选 **自定义机器人**，填名称（比如「后台通知」）→ 添加
3. 复制 **Webhook 地址**，形如 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx-xxxx-…`
4. **安全设置**里勾 **签名校验**，复制出现的密钥 → 保存

安全设置三选一（可以多选），建议只开签名校验：

| 选项 | 建议 | 原因 |
|---|---|---|
| 签名校验 | ✅ | 后台完整支持，地址泄露了别人也发不进来 |
| 自定义关键词 | ❌ | 每条消息都必须含那个词。公告标题、审批标题是用户写的，不一定含 —— 那些消息会被飞书拒掉（`19024`） |
| IP 白名单 | 看情况 | 生产服务器有固定出口 IP 时可以加；本机开发的出口 IP 会变，别开 |

### 2. 在后台登记

**消息推送 → 群机器人 → 新增群机器人**：

| 字段 | 填什么 |
|---|---|
| 名称 | 写成群名，投递记录里显示的就是它 |
| 平台 | 飞书 |
| Webhook 地址 | 第 1 步复制的地址，**整段**粘贴 |
| 加签密钥 | 第 1 步的签名校验密钥 |
| 订阅的通知 | 先勾「通知公告」，最好验证 |

保存后卡片上的地址只剩掩码（`open.feishu.cn/…******` + 末四位）—— 地址本身就是凭据，拿到它就能往群里发，所以不再回显。

### 3. 发测试消息

点卡片上的 **发测试消息**。群里应该出现一条「测试消息」。

没出现的话，页面会弹出原因，卡片上「最近失败」也会留着飞书回的原话：

| 页面上的原因 | 飞书的码 | 怎么办 |
|---|---|---|
| 签名校验没过 | `19021` | 密钥贴错了；或者服务器时钟偏差超过 1 小时（飞书只认 1 小时内的时间戳） |
| 消息里没有机器人设的关键词 | `19024` | 机器人开了「自定义关键词」，见上面那张表 |
| 服务器 IP 不在机器人的白名单里 | `19022` | 去掉 IP 白名单，或者把服务器出口 IP 加进去 |
| 平台说请求格式不对 | `9499` | 一般是地址不完整，重新整段复制 |
| 网络不通 | — | 服务器连不上 `open.feishu.cn`。内网机器要走代理：后端进程设 `HTTPS_PROXY` 环境变量 |
| 保存时报「应以 https://open.feishu.cn/… 开头」 | — | 地址只放行三家官方域名。私有化部署的飞书配 `NOTIFICATION_BOT_EXTRA_URL_PREFIXES` |

### 4. 发一条真的通知

**系统管理 → 通知公告** 里新建一条，状态选「显示」。几秒内群里出现：

```
公告标题
公告《公告标题》已发布，点击查看详情。
查看详情 → （链接）
```

「查看详情」的链接来自 `NOTIFICATION_WEB_BASE_URL`（默认 `http://localhost:8888`）。
同事在自己电脑上点它打不开是正常的 —— 部署到服务器时把它改成真实的访问地址。

去 **消息推送 → 投递记录**，渠道选「群机器人」，能看到这一条：地址列是机器人名称，状态是「已发出」。

### 5. 验完回来告诉我

请记下这几样（截图也行）：

- 测试消息有没有到、群里长什么样
- 公告那一条有没有到、链接点不点得开
- 有没有失败，失败时卡片上的原话

到目前为止三家平台**都还没真发过**：签名算法和错误码分类来自官方文档 + 测试里的假服务器。
你这一次是第一份真实证据，会写进分册的「实测证据」。

## 第二部分：这个功能是怎么设计出来的

### 设计的六个问题

每次加一个功能，都可以按这六个问题走一遍。下面是群机器人走出来的答案。

#### 问题 1：用一句话说清楚，要的是什么？

> 「把一部分通知推到飞书 / 钉钉 / 企微群里。」

听起来很简单，但这句话藏着一个要先回答的问题：**群不是人。**
现有的通知路由是按人算的（策略 × 个人偏好 × 这个人有没有邮箱），群没有邮箱、没有偏好、也不是收件人。

所以真正的需求是：

> 「某类通知发生时，往订阅了它的群里推一条，**和这条通知发给了几个人无关**。」

这一步决定了后面的一切：机器人自己的订阅、一条通知一个群一行、不进个人偏好矩阵。

#### 问题 2：哪些已有的东西可以复用？

先读一期（#166）留下了什么，别急着写新的：

| 已有的 | 能不能复用 | 结论 |
|---|---|---|
| 通知类型注册表 `kinds.py` | 能 | 订阅单位就用通知类型 |
| 投递表 `sys_notification_delivery`（事务内 outbox） | 能，要改一点 | 加 `bot_id`，`user_id` 改可空 |
| worker：抢占、退避、结果未知不重试 | 能 | 只加一个渠道 `bot` |
| 策略 / 偏好矩阵 | **不能** | 那是按人的，群硬塞进去会变成「每个人能不能关掉群消息」，说不通 |

复用的越多，新代码越少，新 bug 也越少。

#### 问题 3：哪里会「坏了不报错」？

这是最值钱的一步。把每一个可能静默出错的地方列出来，每一条都要有测试守着：

| 会怎么静默地坏 | 后果 | 怎么防 |
|---|---|---|
| 一条通知按收件人展开 | 审批结果发给 3 个人，群里出现 3 次 | 一条通知 × 一个群 = 一行投递 |
| 对着本人说话的通知推进群 | 群里每个人读到「抄送给**你**」，单子内容也摊给了整个群 | 类型要声明 `bot=True` 才能被订阅；「被退回」为此拆成了单独类型 |
| 地址随便填 | 有权限的人借服务器去请求内网（SSRF） | 只放行三家官方地址前缀 |
| 地址明文存 | 地址就是凭据，库泄露 = 能往所有群里发 | 加密存，接口只给掩码，操作日志打码 |
| 读超时当成「没发出去」重试 | 群里同一条出现两次 | 请求发出后的超时记「结果未知」，不重试 |
| 不数频率 | 批量审批 30 张单，钉钉第 21 条起全被拒，白耗重试 | 发之前自己数，满了排到下一分钟 |
| 签名算反 | 每条都被拒，界面只说「签名不对」，像是密钥填错了 | 照官方文档写测试，故意算反一次确认测试会红 |

> **这张表当时漏了一行，是接真飞书时才发现的。** 「地址明文存」那一行只想到了数据库和操作日志，没想到 HTTP 客户端自己也会记日志：
> httpx 在 INFO 级别给每个请求打一行 `HTTP Request: POST <完整 URL>`，于是第一次真发，token 就原样进了 `fba_access.log`。
> 消息照发、界面全绿，没有任何症状。
>
> 教训：列「凭据会流到哪」的时候，要顺着数据走一遍它经过的**每一层**（库 → 接口 → 操作日志 → HTTP 客户端 → 应用日志），
> 不要只看自己写的那几层。
>
> **而且第一次修也没修全。** 修在了 API 进程的日志初始化里，测试也是在 API 进程里写的，于是绿了。
> 可真正往群里发消息的是 Celery worker，它有自己的一套日志配置；发了一条真公告，worker 的日志里 token 照样在。
> 第二个教训：**测试要跑在出事的那个进程里**。修法和两条测试见 `common/log.py` 和 `test_bots.py` 里名字带 `log` 的那两条。

#### 问题 4：几个方案，各自错在哪？

拿「订阅关系存在哪」举例，当时想过三种：

| 方案 | 问题 |
|---|---|
| A. 把 `bot` 当成第四个渠道，放进策略矩阵 | 策略是「这类通知走不走这条渠道」，可一个系统里会有好几个群，矩阵里一格表达不了「推给财务群、不推给研发群」 |
| B. 每个群建一个「虚拟用户」，走现有的按人路由 | 能跑，但收件人列表、偏好、地址检查全要对它开特例；还会出现在用户列表里 |
| **C. 订阅存在机器人自己身上（选了这个）** | 机器人 = 地址 + 它订阅的类型列表。通知产生时查一遍「谁订阅了这个类型」 |

方案能跑不代表对：要问「它会在哪种情况下给出一个说得通、但错误的结果」。

#### 问题 5：拿什么证明它是对的？

- 每一条「会静默坏」都对应一条测试
- **测试写完要故意把代码改坏一次**，看它会不会红（变异测试）。不会红的测试等于没写。
  这次就抓到一条：「事务回滚了还会唤醒 worker」那条测试第一版改坏了还是绿的 —— 测试在一个会话里回滚、在另一个会话里提交，根本没测到同一个会话
- 只靠文档推出来的结论要标清楚。钉钉的签名照的是转载的官方示例，就写「按转载」，不写成「已验证」

#### 问题 6：上线时别人要做什么？

- 新的环境变量（`NOTIFICATION_ENCRYPT_SECRET_KEY`）写进 `.env.example` 和发布说明
- 数据库迁移要在每种数据库上跑「升级 → 回滚 → 再升级」。这次就在 SQL Server 上发现：
  被索引的列从「可空」改回「不可空」会被拦下，反方向却放行 —— 只验升级的话，要等真的回滚那天才发现

## 练习

两道题都是这个功能真实的下一步，不是编的。先自己按上面六个问题走一遍、写下答案，再展开参考答案对照。

### 练习 1：财务群只想收「报销」的审批结果

**场景**：公司有「请假」「报销」「采购」三个审批流程。财务群订阅了「审批结果」，现在群里请假的结果也一条条刷屏。
财务说：「我们只要报销的。」

**要你设计**：让一个机器人能只收某几个流程的审批结果。

先回答这几个问题：

1. 用一句话写出需求（注意：「只收报销的」里，「报销」用什么来认？流程名称、ID、还是别的？）
2. 投递行里现在有哪些信息？要按流程过滤，缺什么？这个信息在哪一层才拿得到？
3. 至少想两个方案，各写一句它错在哪
4. 列出至少三种「坏了不报错」的情况
5. 已经在用的机器人，升级之后应该收到什么？

提示：

- 读 `apps/api/backend/plugin/notification/service/notification_service.py` 的 `create_in_tx`，看它收什么参数
- 读 `plugin/workflow/model/workflow.py`，看流程定义上有哪个字段「创建后不可改」
- 想一想：流程是管理员在界面上随时新建的，而通知类型注册表是**代码启动时**就定死的

<details>
<summary>参考答案（先自己写完再看）</summary>

**1. 需求**：「机器人订阅『审批结果』时，可以再限定几个流程（按流程**编码**）；不限定 = 全部流程。」

用编码不用名称：名称管理员随时能改，改了过滤就静默失效（一条都不推，也不报错）；
用 ID 的话每套环境不一样，配置没法跨环境搬。流程定义的 `code` 是「稳定引用键，创建后不可改」，正好是干这个的。

**2. 缺什么**：投递行只有 `kind / title / content / link`，没有「这条通知属于哪个流程」。
这个信息只在**调用方**手里 —— 审批流在 `runtime_service` 里调 `create_in_tx` 时，手上有实例、有流程定义。
所以要给 `create_in_tx` 加一个通用的参数，比如 `tags={'workflow': 'REIMBURSE'}`，由调用方填，路由层按它过滤。

**3. 方案**：

| 方案 | 错在哪 |
|---|---|
| 每个流程注册一个通知类型（`workflow.result.reimburse`） | 注册表是启动时定死的，管理员新建的流程没有对应的类型 |
| worker 发送前按 `link` 里的实例 ID 回查流程 | 通知插件反过来依赖审批插件（依赖方向反了）；发送时实例可能已经变了；卸载审批插件就炸 |
| **`create_in_tx` 加 `tags`，机器人加「过滤条件」** | 通用：以后「只收某个部门的」也是同一个口子。代价是机器人表加一列、迁移一条 |

**4. 坏了不报错**：

- 过滤条件里填了一个不存在的编码 → 永远不推，也不报错。**保存时校验编码存在**
- 「没有过滤条件」被理解成「什么都不推」→ 升级后所有已有机器人突然安静。**空 = 全部**，要写进测试
- 流程被删了 → 过滤条件里留着一个死编码。界面上要标出来（「这个流程已删除」），不要悄悄从列表里消失
- 调用方忘了传 `tags` → 带过滤的机器人一条都收不到。**过滤只对「声明了会传这个标签」的类型生效**，注册表里写明

**5. 已有的机器人**：迁移时新列为空 = 全部流程，行为和升级前完全一样。这一条要有测试：
「没设过滤的机器人，升级后照样收到所有流程的结果」。

</details>

### 练习 2：管理员终止自己发起的单，群里收不到

这一题是**读代码找问题**，答案是从代码推出来的，还没跑过 —— 验证它就是题目的一部分。

**场景**：管理员张三自己发起了一张采购单，后来在「实例监控」里把它终止了。
财务群订阅了「审批结果」，但群里没有出现「已终止」。

**要你做**：

1. 从 `plugin/workflow/service/runtime_service.py` 里 `_finish` 发结果通知的地方开始，一路读到写出群机器人投递行的地方，找出这条消息在哪一步被丢掉了
2. 判断：这是 bug，还是有意的取舍？（提示：「自己的动作不通知自己」对**人**是对的，对**群**呢？）
3. 如果要修，改在哪一层？怎么改才不会把「自己不通知自己」这条对人的规则一起改坏？
4. 写一条测试证明它（先让它红，再修到绿）

<details>
<summary>参考答案（先自己读完代码再看）</summary>

**丢在哪**：两处叠在一起。

- `_Ctx.notify` 先把操作人从收件人里去掉（`if uid != self.actor_id`），去掉之后列表空了就直接 `return`
- 即使走进了 `create_in_tx`，它开头也有 `if not uids: return out` —— 收件人为空就提前返回，**群机器人那一步根本走不到**

所以「群里收不收得到」现在被「这条通知有没有至少一个收件人」绑住了。

**是不是 bug**：对人，「自己点的终止，不用再通知自己」是对的；对群，群里的人并不知道张三终止了单子，应该收到。
所以这是一个**把两种路由塞进同一个入口时带进来的耦合**，算 bug。

**改在哪**：不能删「自己不通知自己」那条（那是对人的规则）。思路是把「发给人」和「发给群」在入口处分开：
收件人为空时，`create_in_tx` 照样要给订阅了的群写投递行。`_Ctx.notify` 那边同理：
过滤完没人了，也要让通知继续走到群那一步。

**测试**：在 `plugin/workflow/tests/` 里造一个场景：机器人订阅 `workflow.result`，发起人自己终止，
断言投递表里有一行 `channel='bot'`。修之前它应该是 0 行（红），修之后 1 行（绿）。
再做一次变异：把修复撤回，确认它又红了。

</details>
