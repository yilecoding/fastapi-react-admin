# pages/menu —— 死链判定（菜单管理）

> `pages/menu/dead-link.ts` 是**唯一实现** —— 计数徽标、行内删除线、「只看死链」筛选、
> 编辑表单的提示全用它。
>
> 这份文件是 [`packages/platform/src/pages` 分册](../AGENTS.md) 的**子分册**，Claude Code 读到本目录下的
> 文件时才把它加载进上下文（惰性加载）。跨模块的硬纪律只在根 `CLAUDE.md` 里有一份；
> **新增结论请追加到离代码最近的那一份**。

判定口径是「**这一条会不会从侧边栏消失**」，
所以规则必须跟 `shell/use-sidebar.ts: toNavTree` 一致，**改一边就要改另一边**。

| 类型 | 规则 |
|---|---|
| 按钮 | 本来就不进侧边栏（只提供 perms） → 从不算死链 |
| 外链 / 内嵌 | 走 `link` 字段，不是前端路由 → 从不算死链 |
| **目录** | **有可见子项时它只是个可展开分组，自己的 `path` 根本不会被用到 → 不算死链**；子项全都进不了侧边栏时才降级成链接，那时才要求 path 有效 |
| 菜单 | 需要自己的 path 有效 |

「有可见子项」必须**递归**算，且与 `toNavTree` 同口径：按钮不算、`display=0` 不算、
**停用的不算**（#143 起停用的那一枝后端整棵不下发，`toNavTree` 见不到它）、自己也是死链的不算。（历史上 `/scheduler` 靠这条判过真死链——上线前两个子项
指向的页面还不存在，自己都是死链；页面补上之后 `/scheduler` 就不再是了，
这条规则不会因为菜单树后续演进而失效，只是不能再拿它当固定例子。）

数据权限还踩过另一种真死链：合并主从页时只删了前端页面，`sys_menu` 种子里
「数据范围」「数据规则」两条 `type=1` 子菜单没跟着清（它们下面各挂着按钮权限点，
删除时要连同把这些按钮重新挂到父级，不能直接删整棵子树）。

> 曾经把目录和菜单一视同仁（`Boolean(path) && !isValidPath(path)`），
> 于是 `/system` `/log` `/monitor` 三个工作得好好的目录被划了删除线、
> tooltip 写着「侧边栏会跳过」，而侧边栏一直正常显示它们 ——
> 59 项里的「8 个死链」有 3 个是假的（修完是 5 个）。
> **种子数据里目录的 path 前端本来就没有对应路由，那是设计如此：目录不该可导航。**

树形筛选会**连着祖先链一起保留**（否则树断成孤立行），所以「只看死链」的行数
会比徽标数多 —— 写断言时对账的是「被标死链的行数」，不是总行数。

## 表单规则前后端各一份

「不同类型必填项不同」原来**只在**本目录 `form.tsx` 的 superRefine 里。直接打接口、或让 AI 建菜单，能建出没有路由地址的菜单、

## 三处「改了、保存成功、界面不变」（#143，已修）

接口全是 200、界面提示保存成功。

### 改内置菜单的标题 → 中文以库为准

**症状**：把「菜单管理」改名成「菜单配置」，保存成功，侧边栏 · 标签条 · 面包屑 · ⌘K · 这一页自己的表格 · 权限矩阵
全都还是「菜单管理」。**根因**：显示一律是 `t(menuKey(path), { defaultValue: title })`，而内置菜单在**两个**语言包里都有
`menu:<path>`，库里的标题永远轮不到。

**修法**：全走 `@admin/i18n` 的 `menuTitle(t, path, title)` —— 基准语言（zh-CN）下直接用库里的标题，其它语言才按 path 查内置译名。
代价是英文界面里改过名的内置菜单仍显示内置译名，所以表单标题下有一行提示（`hasBuiltinMenuTranslation`）。
⚠️ 顺带的可见变化：`/scheduler` 那三条的种子标题（定时任务 / 任务调度 / 执行记录）和中文语言包里的（任务调度 / 任务管理 / 任务记录）
本来就不一样，中文界面现在显示的是种子里的那组。

🔴 **标签条不能用标签自己存的 `title`**：它在打开那一刻定下（路由 `staticData.title` 优先），改了名已开着的标签不跟着变。
标签条 / 标签列表 / ⌘K 的「已打开」按 pathname 现查菜单树（`shell/use-menu-titles.ts`），查不到（个人中心这类）才用存的。

### 停用目录 / 页面 → 连同整棵下级一起关掉

**症状**：停用「系统管理」，侧边栏照常显示，下面「用户管理」的按钮权限照常生效。**根因**：侧边栏只跳过 `display=0`；
权限码逐个菜单算、只看菜单**自己**的 `status`，而目录 / 页面大多不带权限码 —— 只有停用按钮有效果。

**现在的语义**：停用 = 它和全部下级都不生效（侧边栏不下发、下级按钮的权限码失效 → 接口 403、带 `requirePerm` 的页面跳 403）；
「在侧边栏显示」关掉只是不进菜单，照常能用。**只写它自己那一行**，下级是「按上级算」不生效 —— 重新启用就整棵原样回来。
后端的三处改动和「快照里的 status 是生效状态」那条纪律见 [`common/security` 分册](../../../../../apps/api/backend/common/security/AGENTS.md)「停用的菜单按上级算」。

⚠️ 超管不受权限码约束，停用后只是侧边栏里看不到；没挂 `requirePerm` 的页面（仪表盘、个人中心这类）直接敲地址照样进得去。

### 菜单树成环

**症状**：把目录 A 挂到它的孙子 C 下面 —— 接口 200，菜单树里 A、B、C **整棵消失**，库里三行都在。
**根因**：`menu_service.check_update` 只拦「上级是自己」；前端上级下拉排除了自己那棵子树，直接打接口 / AI 工具就绕过去了。
**修法**照部门 #135：`menu_dao.get_ancestor_ids` 查新上级的祖先链里有没有自己 → 403。
