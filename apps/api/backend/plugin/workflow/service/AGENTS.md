## 拿回：恢复的是「同意之前的实例变量」，不只是那条待办

能拿回 = 这张单**最近一次推进**（`_PROGRESS` 里的动作）是我的同意 / 加签，且之后新建的待办都还没人动。
同意时把「同意之前的 `variables`」和「这次新建了哪些待办」记在 `variables['undo']`。

🔴 **只重建那条待办不够，实例变量要一起恢复**：同意会消费东西（直达标记、加签组）。
实测：赵磊的同意用掉了「直达 n3」，不恢复变量的话拿回后再同意就不再直达 n3（断言 `current == n3` 红）。
`test_take_back_restores_the_resume_jump` 守着（变异：不恢复变量 → 红）。
⚠️ 第一版只有「拿回加签」那条测试，同样的突变下**照样绿**：加签组就算残留，赵磊再同意时他不是组员、
照常往下走，结果碰巧一样。守这条不变式要用「同意消费过状态」的场景。

「最近一次推进是我」和「新建的待办都还没人动」是**互为兜底的两道**：超时自动同意（系统动作）
加进来之后，`_PROGRESS` 里有 `timeout_approve`，两道都能挡住「下一步已经被超时处理了还想拿回」。
变异验证：只去掉一道，`test_no_take_back_after_the_next_step_timed_out` 照样绿；两道一起去掉才红。

### 🔴 或签拿回还要恢复本次取消的其他审批人待办（#306）

**症状**：A / B 或签，A 同意或「在我之后」加签，再拿回，只有 A 重新有待办，B 的待办没有回来。
**根因**：撤销快照只存新建待办和实例变量，没有记本次取消的同节点待办。
**修法**：两条取消路径把实际取消的待办 ID 记进 `undo.canceled`；拿回按历史行的办理人、姓名、`batch`、
`origin_assignee_id` 重建，并通过原有新待办通知和提交后刷新待办的机制通知所有恢复的办理人。
不要重新解析审批人规则，也不要扫描同节点所有 canceled 行——那会恢复转交前的人或之前轮次的历史待办。
旧撤销快照没有 `canceled` 字段时仍按原行为处理；本修复不推断历史上缺失的撤销快照。

**实测证据**（2026-11-13，独立 SQL Server 测试库与 Redis）：`test_take_back_restores_every_canceled_or_task`
覆盖普通同意 / 后加签 × 原办理人 / 已转交四种组合，每种连续拿回两次，随后由另一位审批人完成办理；
修复前四种组合都因缺少待办失败，修复后通过。另有 `test_take_back_after_sign_is_rejected_once_a_member_acts`
验证加签成员已转交时仍不许拿回。新增回归共 5 条通过。
整个审批插件测试集在同一临时 SQL Server 环境为 172 passed / 14 skipped。
