There are three ways to sign in: username and password, an SMS code, or a GitHub / Google account. Once the identity is confirmed, all three go through the same two-factor step (a TOTP code, or a recovery code if the phone is lost). Facing outward there are two layers of failure lockout (per account and per IP) and an image captcha. Inside, every sign-in is a server-side **session** with its own rules for how long it may sit idle, how long it may last at most, and how many sessions one account may hold, set separately for web, desktop and mobile. Admins can see every session under Active sessions and sign any of them out; the person on the other end is sent straight back to the sign-in page with the reason, not a generic "please sign in again".

## Where is it in the UI?

| Screen | Path | Who | What it does |
|---|---|---|---|
| Sign-in page | `/sign-in` | Everyone | Password / SMS code / third-party sign-in; the TOTP code is a second step |
| **Profile** | `/profile` | The user | Change password · bind a phone number · turn two-factor on or off, regenerate recovery codes · link third-party accounts · recent sign-ins |
| **System → Users** | `/system/user` | Superusers | Reset someone's password · reset someone's two-factor (lost phone) |
| **Monitoring → Active sessions** | `/monitor/online` | Superusers | Every session on the site · force sign-out |
| **System → Config** | `/plugins/config` | `sys:config:edit` | The **Sign-in policy**, **Passwords & lockout** and **Sessions** groups; see [below](#which-settings-are-there) |
| **Logs → Sign-in log** | `/log/login` | `log:login:list` | Every sign-in attempt with result, IP and browser |

Resetting a password, resetting two-factor, listing active sessions and forcing a sign-out are guarded by **superuser** (`DependsSuperUser`), not by permission codes: give an ordinary role the Active sessions menu and the page opens, but the API refuses.

## Which sign-in methods are there?

| Method | Requires | Notes |
|---|---|---|
| Username and password | — | Image captcha on by default |
| SMS code | The SMS plugin (`plugin/sms`) | Only numbers **the user verified themselves** in Profile count. A number typed in or imported by an admin does not: one wrong digit and the owner of that number could sign in to someone else's account |
| GitHub / Google | The OAuth2 plugin, with Client ID / Secret in `.env` | An unknown third-party account is **refused by default** and told to sign in with a password first and link the account in Profile. To allow self-registration, set `OAUTH2_AUTO_REGISTER=true` and name the role with `OAUTH2_AUTO_REGISTER_ROLE` |

There is no self-service password recovery: the sign-in page says "Ask an admin to reset your password".

The SMS route requires the image captcha first; each number has a 60-second cooldown and at most 10 codes a day. **Numbers that are not registered or not verified still get "sent"**, though nothing is actually sent: status code, message, cooldown and response time all match a real send, otherwise this anonymous endpoint would be a lookup table for which numbers have accounts. When the SMS provider is down the response is the same success; the failure is recorded in the SMS log for admins.

## How many wrong passwords before a lockout?

Two counters, each for a different attack:

- **Per account**: 5 failures in a row lock the account for 5 minutes (changeable under Config → Passwords & lockout; a threshold of 0 disables it). This stops guessing one account's password.
- **Per IP**: 30 failures from one IP, across any number of accounts, lock that IP for 15 minutes (`.env` only). This stops password spraying: 200 usernames tried 4 times each stay under the per-account threshold of 5 and never trigger a lockout. It depends on `TRUSTED_PROXIES` being set, or every request appears to come from the reverse proxy.

The error message **does not distinguish** "no such user", "wrong password" and "account locked", and the timing is evened out too: a bcrypt check takes about 190 ms, while a lookup that finds no user takes about 5 ms, a 40x gap that needs no statistics to spot. So when the user does not exist, an equivalent check runs against a dummy hash (`_DUMMY_PASSWORD_HASH` at the top of [`auth_service.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/app/admin/service/auth_service.py)).

The sign-in endpoints are also rate-limited per IP and path: 5 a minute; the captcha endpoint allows 5 every 30 seconds.

## What are the password rules?

| Rule | Default | Allowed range |
|---|---|---|
| Length | 6–32 characters | 1–128 |
| Must contain a special character | No | — |
| Cannot repeat one of the last N passwords | 3 | 0–24 |
| Valid for | 365 days (0 = never expires) | 0–3650 |
| Reminder lead time | 7 days (0 = no reminder) | 0–365 |

The allowed ranges are enforced by the **backend**, not just by the input boxes (`DYNAMIC_INT_BOUNDS` in [`dynamic_config.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/utils/dynamic_config.py)). It was tested once: calling the API directly with an admin token could set the minimum length to 999, after which nobody could change their password.

Changing your own password, or having it reset by an admin, ends **every** session of that account (reason: password changed), including the current one.

:::caution[Two gaps around password expiry]
- Once the reminder window starts, the sign-in response includes `password_expire_days_remaining`, but **the web client does not show it yet**.
- After expiry, password and SMS sign-in are both refused (third-party sign-in does not check password age). The message says to change the password and sign in again, but the user can no longer sign in to do so; only a superuser can reset it under Users.
:::

## How does two-factor (MFA) work?

Any authenticator app works (Google Authenticator, Microsoft Authenticator, 1Password, …). It is standard TOTP: 6 digits, a new code every 30 seconds, SHA-1, one time step of clock drift tolerated either way, and **the same code cannot be used twice**. There are also 10 single-use recovery codes (`xxxx-xxxx`, without the easily confused 0 / O / 1 / I / L); each works once, and only their hashes are stored.

- **Turning it on yourself**: scan the QR code in Profile → enter one code to confirm → the recovery codes are shown **this one time only**. Later, with a valid code, you can generate a new batch (the old ones stop working) or turn it off.
- **Requiring it**: **Require two-factor** under Config → Sign-in policy has three levels: `off` (optional), `superuser` (superusers must), `all` (everyone must). Someone who is required but has not enrolled scans the QR code during their next sign-in and cannot get in until they do; someone who is required cannot turn it off.
- **Lost phone**: a superuser resets that person's two-factor under Users. If they are required to use it, they enrol again at next sign-in.

All three sign-in methods pass this step (SMS and third-party sign-in ask for the code too), and the mobile app can enter it as well. Someone who is required to enrol but has not yet is told by the app to do it on the web first. The second step allows 5 minutes and 5 attempts. **A wrong code counts toward the account's password failures**, and a correct password no longer resets that count; it is reset only after the second step passes. Otherwise every sign-in would allow 5 guesses and then reset, which amounts to unlimited guesses at a 6-digit number.

:::note[Set the key first]
TOTP secrets are encrypted at rest with `MFA_SECRET_KEY` from `.env` (64 hex characters). **While it is empty, two-factor cannot be turned on and the policy cannot be set to required**; secrets are never stored in plain text instead. Requiring two-factor without a way to enrol would lock out everyone it applies to, including the admin who changed the setting. Generate one with `python -c "import os;print(os.urandom(32).hex())"`.
:::

## How many devices can one account use, and when does an idle session end?

Each sign-in creates a session on the server, and its ID stays the same until it ends. The client says which kind it is when signing in, and each kind has its own rules:

| | Web | Desktop | Mobile |
|---|---|---|---|
| Idle timeout | 120 minutes | 120 minutes | 30 days |
| Maximum lifetime (from sign-in; activity does not extend it) | 7 days | 7 days | 90 days |
| Sessions per account on this client | Unlimited | Unlimited | 1 |
| When the limit is reached | Sign out the least recently active | Sign out the least recently active | Sign out the least recently active |

All of these are under Config → Sessions; the over-limit behaviour can also be "refuse the new sign-in". For single-device sign-in, set the limit to 1. Changes apply to **later** sign-ins only; existing sessions keep the rules they started with.

**Idle means the person stopped using it, not that requests stopped.** Active sessions polls every 10 seconds, monitoring pages and export progress also make background requests. Counting requests would keep a session alive forever while the person is away and the browser is open, exactly what an idle timeout is supposed to catch. So every request from the browser carries how many seconds have passed since the last keyboard, mouse or touch input, and the server works out the last activity from that; for someone who keeps scrolling or typing without triggering a request, the client sends a heartbeat every 5 minutes.

The access token lasts 30 minutes and is renewed with the refresh token, which is replaced each time it is used. Presenting the previous refresh token within 30 seconds (several tabs refreshing at once, a retry on a bad network) returns the same new pair; presenting it later is treated as possible theft and **the whole session ends immediately**.

## What does a signed-out person see?

When a session ends the server records why; the next request from that person gets a 401 carrying the reason, and the page goes back to the sign-in screen with the message:

| Reason | Message on the sign-in page |
|---|---|
| Forced sign-out by an admin | You were signed out by an administrator, please sign in again |
| Pushed out by the session limit / signed in again in the same browser | Your account signed in on another device, so this device was signed out |
| Idle timeout | You were signed out after a period of inactivity, please sign in again |
| Maximum lifetime reached | Your session has expired, please sign in again |
| Password changed or reset | Your password was changed, please sign in again |
| Account disabled or deleted | Your account has been disabled, please contact the administrator |
| Refresh token reused | Your sign-in credentials were used more than once, so you were signed out; change your password if this wasn't you |

Active sessions lists every session on the site: user, client type, whether it has a live connection, IP, browser, operating system, sign-in time, last activity and time left. After **Force sign-out**, the other person's open page jumps to the sign-in screen over the live connection right away, without waiting for their next click. Within one browser, signing out in one tab sends the other tabs back to the sign-in page too.

## Which settings are there?

**Changed in the UI** (System → Config), effective from the next sign-in, no restart:

| Group | Key | Default | Notes |
|---|---|---|---|
| Sign-in policy | `LOGIN_CAPTCHA_ENABLED` | `true` | Image captcha; turning it off applies to everyone at once |
| Sign-in policy | `LOGIN_MFA_ENFORCE` | `off` | `off` / `superuser` / `all`; must stay `off` while `MFA_SECRET_KEY` is empty |
| Passwords & lockout | `USER_LOCK_THRESHOLD` · `USER_LOCK_SECONDS` | `5` · `300` | Failures before lockout, and for how many seconds; 0 = never lock |
| Passwords & lockout | `USER_PASSWORD_MIN_LENGTH` · `USER_PASSWORD_MAX_LENGTH` | `6` · `32` | |
| Passwords & lockout | `USER_PASSWORD_REQUIRE_SPECIAL_CHAR` | `false` | |
| Passwords & lockout | `USER_PASSWORD_HISTORY_CHECK_COUNT` | `3` | Cannot repeat the last N |
| Passwords & lockout | `USER_PASSWORD_EXPIRY_DAYS` · `USER_PASSWORD_REMINDER_DAYS` | `365` · `7` | 0 = never expires / no reminder |
| Sessions | `SESSION_{WEB,DESKTOP,MOBILE}_IDLE_MINUTES` | `120` · `120` · `43200` | 5 minutes to 90 days |
| Sessions | `SESSION_{…}_ABSOLUTE_DAYS` | `7` · `7` · `90` | 1–365 |
| Sessions | `SESSION_{…}_MAX` | `0` · `0` · `1` | 0 = unlimited |
| Sessions | `SESSION_{…}_OVERFLOW` | `evict_idle` | Or `deny` to refuse the new sign-in |

Each group also has a master switch, `<GROUP>_CONFIG_STATUS`; set to 0, the whole group is ignored and the `.env` values apply. The other way round, **setting these keys in `.env` has no effect while the database rows are on**, which is the cause of the FAQ entry [captcha still required after disabling it in `.env`](/en/reference/faq/#login_captcha_enabledfalse-is-set-in-env-but-sign-in-still-asks-for-a-captcha).

**`.env` only**, restart the backend after changing:

| Key | Default | Notes |
|---|---|---|
| `MFA_SECRET_KEY` | empty | Encrypts TOTP secrets; empty = two-factor cannot be turned on |
| `LOGIN_IP_LOCK_THRESHOLD` · `LOGIN_IP_LOCK_SECONDS` | `30` · `900` | Per-IP lockout across accounts; threshold 0 = off |
| `TRUSTED_PROXIES` | `[]` | Addresses or ranges of your reverse proxies. Empty = no forwarding header is trusted; behind a proxy without it, the backend sees only the proxy's IP, so IP lockout, rate limits and the sign-in log all use the wrong address |
| `TOKEN_EXPIRE_SECONDS` | `1800` | Access token lifetime |
| `SESSION_REFRESH_GRACE_SECONDS` | `30` | Grace period for the previous refresh token; production refuses anything under 10 seconds |
| `LOGIN_CAPTCHA_EXPIRE_SECONDS` | `300` | Image captcha lifetime |
| `MFA_CHALLENGE_SECONDS` · `MFA_CHALLENGE_ATTEMPTS` | `300` · `5` | Time and attempts allowed for the second step |
| `COOKIE_SECURE` | follows the request | HTTPS requests get a `Secure` cookie. If a proxy terminates TLS and rewrites `X-Forwarded-Proto` to `http`, set it to `true` explicitly |
| `OAUTH2_GITHUB_*` · `OAUTH2_GOOGLE_*` | — | Client ID / Secret for third-party sign-in |
| `OAUTH2_AUTO_REGISTER` · `OAUTH2_AUTO_REGISTER_ROLE` | `false` · — | Whether unknown third-party accounts get an account, and with which role (an unknown role code refuses the sign-in) |

The full definitions are in the user security, sign-in and session sections of [`core/conf.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/core/conf.py).

## What to watch when adding a sign-in method or a way to sign someone out

- **A new sign-in method must call `mfa_service.gate()`** after confirming the identity; it decides whether to open the session or ask for the second step. SMS sign-in repeats every check that password sign-in makes (IP lockout, disabled accounts, password expiry, failure counting); the code replaces only the "is the password right" step. Reusing just the "open a session" part would skip all of them.
- **A new endpoint that works without signing in** goes into `TOKEN_REQUEST_PATH_EXCLUDE` as a full path, not a prefix.
- **A new way to sign someone out** calls only `session_store.revoke` / `revoke_user`; do not delete the `fba:session*` Redis keys yourself. Those two functions also record the reason, push the live message and close the connection. Before sessions were reworked, seven files each deleted tokens on their own, and one deleted only the access token, so a kicked user could refresh and be back.

Details and the pitfalls behind them are in the sign-in sessions section of [`common/security/AGENTS.md`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/common/security/AGENTS.md).

## What it does not do

- The only second factors are TOTP and recovery codes: no passkeys (WebAuthn), no hardware keys, and SMS is not offered as a second factor.
- No self-service password recovery or self-registration (except third-party sign-in with auto-registration explicitly turned on).
- The password expiry reminder is not shown in the web client yet, and an expired password cannot be changed by its owner; see [above](#what-are-the-password-rules).
- Session operations are Redis Lua scripts written for a single Redis instance; they have not been tested on Redis Cluster.

## How is it tested?

Backend tests run against a real database and Redis:

- [`test_session.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/api_v1/test_session.py) (29 tests): background polling does not keep a session alive, coming back after the idle limit and clicking once does not revive it, the grace period replays the same pair, presenting an old token after it ends the session, and a matching session ID with the wrong secret does **not** revoke anything (otherwise a session ID seen in a log would be enough to sign someone out). Several were mutation-checked: break the condition and the test fails immediately.
- [`test_mfa.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/api_v1/test_mfa.py) (16 tests): recovery codes work once, a correct password does not reset the failure count, the token dies after too many attempts, required users enrol during sign-in and cannot turn it off, and it cannot be required without a key.
- [`test_auth.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/api_v1/test_auth.py): an unknown user and a wrong password look the same, **including timing**; a wrong password does not reveal a lockout; a forced sign-out also revokes the refresh token.
- [`test_phone_login.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/plugin/sms/tests/test_phone_login.py): unknown and unverified numbers look "sent", a provider failure is indistinguishable from an unknown number, and SMS sign-in also requires two-factor.
- The OAuth2 plugin's [`tests/`](https://github.com/yilecoding/fastapi-react-admin/tree/main/apps/api/backend/plugin/oauth2/tests): unknown accounts are not auto-created by default, state binding, only verified emails are trusted.

In the browser (Playwright): [`mfa.spec.ts`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/web/e2e/tests/mfa.spec.ts) (turn it on in Profile → sign out → signing in asks for a code), [`session.spec.ts`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/web/e2e/tests/session.spec.ts) (a forced sign-out sends the page back to the sign-in screen with the reason; signing out in one tab signs out the others; if the backend is briefly unreachable during a refresh, the page shows "can't reach the server" instead of signing out), and [`login-phone.spec.ts`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/web/e2e/tests/login-phone.spec.ts).

## Try it on the demo

On the [live demo](https://fra.wubunan.com/sign-in) (`admin` / `123456`), sign in from two browsers (or a normal and a private window). Under Monitoring → Active sessions you will see both sessions with their client type, browser and last activity. Force **your own other session** to sign out and that window goes back to the sign-in page with the reason. Everyone shares `admin` on the demo, so don't sign out other people's sessions; the demo is also not guaranteed to have `MFA_SECRET_KEY` set, so try two-factor locally.
