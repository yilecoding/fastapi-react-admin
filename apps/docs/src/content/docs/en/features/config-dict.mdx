**Config** is a key / value table. When the backend needs a group of settings it reads them from the database and overrides the same keys from `.env`, so a change an admin makes in the UI needs no restart. The page is grouped by purpose (sign-in policy, passwords and lockout, sessions, email, notification delivery, webhooks, file uploads, log…), and each item has a description, a unit and an allowed range; the backend validates the range on write, so a bad value never lands in the database. The **data dictionary** is a separate table: a "dictionary type" with a list of items (label, value, colour, sort order), meant for drop-down options and status labels in business pages.

## Where is it in the UI?

| Screen | Path | Needed to open the page | Other permission codes |
|---|---|---|---|
| **System → Config** | `/plugins/config` | `sys:config:edit` | View `sys:config:list` · **Add key** `sys:config:add` · delete `sys:config:del`; each row's **Change history** needs `log:change:list` |
| **System → Data dictionary** | `/plugins/dict` | `dict:type:add` | Types `dict:type:list` · `edit` · `del`; items `dict:data:list` · `add` · `edit` · `del` · `import` · `export` |

⚠️ As with several other admin screens, these two pages' frontend route guards check the edit / create code rather than the view code, so a role granted only viewing cannot open them.

## How soon do changes apply, and can they break things?

- **No restart.** A write clears the cache, and the next read picks up the new value: sign-in and captcha settings are read on every request, email on every send, webhook and retention values straight from the database each time. Two groups only affect what comes after: **Sessions** apply to later sign-ins (existing sessions keep the rules they started with) and **File uploads** to uploads that start afterwards.
- **Each group has a master switch**, `<GROUP>_CONFIG_STATUS`. Set to `0`, the group is not read from the database and the `.env` values apply. Conversely, while the group is on, **database values override `.env`**, which is why turning the captcha off in `.env` does nothing (see the [FAQ](/en/reference/faq/#login_captcha_enabledfalse-is-set-in-env-but-sign-in-still-asks-for-a-captcha)).
- **The backend validates writes**, not just the input boxes: integers have bounds (minimum password length 1–128, session idle time 5 minutes to 90 days, for example), fixed-choice keys accept only their values, and two-factor cannot be made mandatory while `MFA_SECRET_KEY` is unset. It was tested once: without this check, calling the API directly with an admin token could set the minimum password length to 999, after which nobody could change their password.
- **Reads have a fallback too**: an invalid value in the database (emptied, out of range) falls back to the `.env` value for that item with an error logged, rather than making sign-in fail with a 500.

## Can I add my own config keys?

Yes, with **Add key**. Two things to know:

- Your own keys land in **Unmanaged keys**, with no description, unit or range check. The group drop-down only offers sign-in, passwords & lockout, email and AI.
- **The backend has no generic way to read them**: built-in items override `settings` because each one is mapped in code. Business code has to query the config table itself to use a key you added.

To add a runtime setting **like the built-in ones** (described, bounded, overriding `.env`), see the developer section below.

## What is the data dictionary?

Two levels:

- **Dictionary type**: name, code (unique), remark.
- **Dictionary item**: its type's code, label, value, colour, sort order, status (normal / disabled), remark. Labels are unique within a type.

Business code fetches a type's options with `GET /api/v1/sys/dict-datas/type-codes/{code}`, which returns only enabled items, sorted by sort order **descending**; the result is cached in Redis for 2 hours and the cache is cleared when items change. Items can be [imported and exported](/en/features/import-export/), matched to existing items by type code + label.

⚠️ **None of the built-in pages read the dictionary yet**: labels like notice type or status are hard-coded in each page, and only the dictionary page itself calls the dictionary API. The dictionary is there for your own business pages, and the frontend has no ready-made "fetch a dictionary type" hook yet.

## Which settings are there?

Config and the dictionary have no further switches. `dict` is a **required plugin** (`PLUGIN_REQUIRED` in `.env`) and cannot be uninstalled.

## For developers: adding a runtime setting

1. Seed data: add a row to each of the five init SQL files under `plugin/config/sql/`.
2. Write a data migration that inserts the row with `insert_if_absent`; running databases never re-run seed SQL, so without a migration only new installs get the key.
3. Declare the key in `core/conf.py` with a default, which is the fallback when the group is off or the value is invalid.
4. Add it to the group's `load_*` mapping ([`utils/dynamic_config.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/utils/dynamic_config.py)) and make sure that `load_*` is called on the code path that reads the setting; a new group also needs a `ConfigType`.
5. Add integers to `DYNAMIC_INT_BOUNDS` with the same `min` / `max` in the frontend's `pages/config/registry.ts`; `test_dynamic_config_bounds.py` checks the two agree. Fixed-choice keys go into `DYNAMIC_CHOICES`.
6. Add the description, unit and widget to `REGISTRY` in `registry.ts`; a new group also needs a nav entry, an icon and Chinese / English strings.

Rules and pitfalls are in [`pages/config/AGENTS.md`](https://github.com/yilecoding/fastapi-react-admin/blob/main/packages/platform/src/pages/config/AGENTS.md).

## What it does not do

- **Password-like values are only hidden on screen**: keys whose name looks like a secret, such as the email password, are shown in a password box that can be revealed, but the API returns them in plain text, so anyone who can open the Config page can read them. Data change history records only that they changed, not the value.
- Keys you add yourself have no validation and no generic accessor; the "visible to frontend" flag has no effect in the backend.
- Editing or deleting a dictionary **type** does not clear the dictionary cache, so the change can take up to 2 hours to show; changing a type's code does not update its items' type code.
- The dictionary page's colour options don't match the colours used in the seed data, so some seeded items show the default style.
- Neither the Config page nor the dictionary page has a dedicated E2E test.

[`test_upload_policy_config.py`](https://github.com/yilecoding/fastapi-react-admin/blob/main/apps/api/backend/app/admin/tests/api_v1/test_upload_policy_config.py): the file upload group. `test_mfa.py` covers "two-factor cannot be required without a key" and "the config list does not 500 because of one old value that no longer validates".
- Dictionary import and export are covered in `test_import.py` and `test_export.py`.
- No dedicated browser tests; the E2E global setup turns off the image captcha through the Config API.
