After sign-in the first page is the **dashboard**: a set of cards (Waiting on me, My requests, Quick start, Shortcuts, Messages for me, Announcement, Needs your attention, Service status, Sign-ins over the last 14 days). Each person chooses which to show, in what order and how wide; the layout is stored on the server, so signing in on another computer brings back the same one, and cards someone has no permission for never appear. Around the dashboard the interface has a few shared tools: the ⌘K command palette, keyboard shortcuts, a product tour on first sign-in, appearance settings in Profile, column visibility and order on lists, a per-user time zone and language, and a refresh prompt when a new version is deployed. Tabs are covered separately in [Multi-tab](/en/features/multi-tab/).

## Where is it in the UI?

| What | Where | Stored |
|---|---|---|
| Dashboard and the **Custom** button | Dashboard `/dashboard`, every signed-in user | Server, per user (all devices) |
| Command palette | ⌘K / Ctrl+K on any page | — |
| Keyboard shortcuts | Press `?`, or **Help** in the top bar | — |
| Product tour | Starts on first sign-in; replay from **Help → Product tour** or the command palette | Browser, per user |
| Appearance and layout preferences | Profile → **Theme** / **Layout** / **Tabs** | Browser |
| Display time zone | Profile → **Profile** | Server, per user |
| Language | User menu at top right → **Language**; also on the sign-in page | Browser |
| List **Columns** | At the right of each list's header | URL |

## Which cards are there, and who sees them?

| Card | Content | Who sees it | Default |
|---|---|---|---|
| Waiting on me | Up to 6 items, tabs All / To approve / Returned to me / Draft | People with the approval center in their sidebar | 2/3 width, shown |
| My requests | Progress bars for the last 3 requests; **Remind** after a day without movement | same | 1/3, shown |
| Quick start | 4 workflows you can start | same | 1/3, shown |
| Shortcuts | Pages picked from your own sidebar, 6 by default, up to 12 | everyone | 1/3, shown |
| Messages for me | 4 unread messages, the same data as the bell | everyone | 1/3, shown |
| Announcement | 5 notices | everyone | full width, **hidden by default** |
| Needs your attention | Auto-disabled webhooks, failed jobs in the last 24 hours, an unusual rise in failed sign-ins today | Anyone with `open:webhook:list`, `task:scheduler:edit` or `log:login:list` | 1/2, shown |
| Service status | API / database / cache / scheduler / worker, plus online sessions per client | Superusers | 1/2, shown |
| Sign-ins, last 14 days | Daily bars of successful / failed sign-ins | `log:login:list` | full width, shown |

**Cards without permission are not rendered**, rather than rendered as an empty "no access" shell, and the backend endpoints behind them check the same conditions. The "System" group appears only for people who can see at least one of its cards.

## How do I customise the dashboard?

Click **Custom** at the top right to enter edit mode (the URL gains `edit=true`, which survives a reload):

- Show or hide each card
- Drag to reorder, or use the keyboard (space to pick up, arrow keys to move, space to drop); each group is ordered separately
- Four widths: 1/3, 1/2, 2/3, Full
- Choose which pages go in **Shortcuts**
- **Restore defaults**

The layout is stored per user on the server (table `sys_user_preference`, key `dashboard.layout`), the same in any browser on any computer. Compatibility rules keep upgrades from breaking it: unknown cards are ignored, new cards are appended at the end, and one bad field falls back for that field only; a layout that cannot be read at all shows a warning and the default layout. **If loading the layout fails**, an error is shown with the default layout and **editing is disabled** (otherwise saving would overwrite the real layout on the server); if saving fails, the error stays in the editor and the draft is kept.

## Command palette and shortcuts

Press **⌘K** (Ctrl+K on Windows / Linux) to open the command palette. It searches three kinds of things:

- **Open tabs**
- **Pages**: pages in your own sidebar (ones already open are not repeated), external links included
- **Actions**: Reload this page, Close other tabs, Close all tabs, Keyboard shortcuts, Product tour; actions that cannot run right now are not listed

Matching is in order (the typed characters appear in order in the name, path or hint), with name matches ranked first. The palette **does not search business data** and has no "recent" list.

Shortcuts:

| Keys | Action |
|---|---|
| ⌘K / Ctrl+K | Open the command palette |
| ⌘B / Ctrl+B | Collapse / expand the sidebar |
| `?` | Keyboard shortcuts (not triggered while typing in an input) |
| ↑ ↓ · Enter · Esc | Choose, open, close in the palette |
| Middle-click a tab | Close it (can be turned off in preferences) |
| Right-click a tab | Tab menu |

## What is the product tour?

A seven-step tour that starts the first time you reach the dashboard: sidebar → tabs → page content → command palette → notifications → profile → help. If a notice pops up after sign-in, the tour waits until it is closed. To see it again, use **Help → Product tour** in the top bar or the command palette. People who turned tabs off skip that step automatically.

"Seen" is stored **in the browser** (per user and tour version), so it appears once more on a new computer.

## What can be adjusted in the appearance?

In the **Theme**, **Layout** and **Tabs** sections of Profile; changes apply immediately and there is no save button:

| Setting | Default | Options |
|---|---|---|
| Theme mode | Light | Light / Dark / System |
| Accent color | Indigo | 7 colors |
| Corner radius | Soft | 6 levels |
| Interface density | Standard | 5 levels (24–36 px controls) |
| Scroll behavior | Content area | Content area (top bar and tab bar stay put) / Whole page |
| Show tab bar | On | |
| Tab appearance | Card | Button / Card / Soft / Underline |
| Tab icons · middle-click to close · drag to reorder | On | |

These are stored **in the browser** (`admin:prefs` in `localStorage`) and do not follow the account: another browser starts from the defaults. **Restore defaults** resets all of them (tours already seen are kept). The sign-in page follows the theme too, and has its own theme and language switches.

## Columns, pagination and filters on lists

- **Columns**: the **Columns** button at the right of the header lets you tick which columns show and drag to reorder them. The choice goes into the URL (`hide=` for hidden columns, `cols=` for an order that differs from the default), so it survives a reload and a shared link shows the same columns; **Restore defaults** removes both parameters.
- **Pagination**: 10 / 20 / 30 / 50 rows, 20 by default; written to the URL only once changed.
- **Filter bar**: press Enter to search; when conditions have changed but not been applied, a line says "Filters changed — press Enter to apply", and input is validated before searching; conditions can be added and the bar collapsed. Conditions go into the URL and **Reset** clears them. **Saved views** (named sets of conditions) are stored only in the browser, and the UI says so.

## Time zone and language

- **Time zone** is per person, set under Profile → **Profile**, default `Asia/Shanghai`. It **only changes how times are displayed** (lists, details, the dashboard greeting and where "today" starts, times in exported files); it does not change when logs were recorded or which time zone scheduled jobs run in. After changing it, tabs that are already open convert times once their data is refreshed.
- **Language** is Simplified Chinese or English, switched from the user menu or the sign-in page and stored in the browser; requests then carry `Accept-Language`, so backend messages, config names, endpoint descriptions and the like switch language too. Business data entered by users is not translated.

## How do people find out about a new version?

Every 10 minutes, and whenever the browser tab regains focus (at most once a minute), the frontend fetches `/version.json` and compares it with the version it was built with; it also catches the "failed to load page code" errors that only happen after a deploy. When a new version is found, a toast that stays until dismissed says "A new version is available" with a **Refresh** button. **It never reloads by itself**: the user may be in the middle of a form.

## Adding a dashboard card

1. Add an entry to [`dashboard/cards/registry.ts`](https://github.com/yilecoding/fastapi-react-admin/blob/main/packages/platform/src/pages/dashboard/cards/registry.ts): `id`, group, title, `available` (who sees it), default width, default visibility.
2. Write the component under `cards/`, wrapped in `DashboardCard`.
3. **Make `available` match the permission check of the endpoint it reads**, one endpoint per card; otherwise the card shows and the request gets a 403.
4. Add strings to both locale files.
5. **Never change a card's `id`**: saved layouts identify cards by it, so a rename means one card removed and a new one added.

**Adding a command palette action**: add it to `actionItems` in [`shell/command-menu.tsx`](https://github.com/yilecoding/fastapi-react-admin/blob/main/packages/platform/src/shell/command-menu.tsx); new pages appear automatically once they have a menu row. **Adding a shortcut** has no registry: add your own listener, call `preventDefault` for modifier combinations, check that single keys are not typed into an input, and add a line to `shortcuts-dialog.tsx`. **Adding a tour step**: add the step in `shell/tour/shell-tour.ts`, put `data-tour` on the target element (`pnpm arch:check` fails if the target does not exist), and bump the version if people who saw it should see it again.

## What it does not do

- Appearance preferences, language, saved views and "tour seen" live only in the current browser and are not synced with the account; only the dashboard layout and the time zone are stored on the server.
- There is only the one shell tour; per-page tours do not exist yet.
- The command palette does not match pinyin initials.
- Changing the time zone does not convert already-open tabs until their data is refreshed.
- Quick ranges like "today" in the filter bar use the browser's local time, while the dashboard's "today" uses the display time zone; when the two differ, a details link from the dashboard may be off by a day (inferred from the code, not covered by a test).
